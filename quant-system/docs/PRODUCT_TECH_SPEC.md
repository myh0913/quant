# 量化系统产品与技术规格书

> 版本：v0.3 草案
> 日期：2026-09-06
> 状态：首期产品决策已确定；数据源当天链路已基本验证；待进入适配器设计

## 1. 产品目标

构建一个可迁移、可复现、可回测的量化选股与股票操作建议系统。系统从历史或实时市场数据中计算因子，运行策略和风险规则，输出可解释的股票建议；不自动下单，用户自行执行交易。

## 2. 用户与使用场景

用户为个人投资者和研究者，主要使用系统完成：

1. 研究因子和策略是否具有稳定性。
2. 对历史数据进行严格回测。
3. 在模拟运行中生成假设建议。
4. 在实时运行中获得股票操作建议。
5. 记录建议、人工操作和后续结果，进行策略归因。

## 3. 产品范围

### 3.1 必须支持

- 历史数据导入、标准化、质量检查和本地存储。
- 因子计算与版本记录。
- 可插拔策略接口。
- 组合、仓位和风险检查。
- 考虑交易成本和市场约束的回测。
- 模拟盘运行。
- 只读式实时建议。
- 建议、人工成交和市场结果记录。
- 运行日志、异常告警和数据新鲜度检查。
- 一键初始化、校验和迁移说明。

### 3.2 明确不做

- 自动连接券商或自动下单。
- 让 LLM 直接决定买卖或修改风控。
- 未经验证的机器学习预测作为第一版核心。
- 一开始建设微服务、Kafka、Kubernetes 等复杂基础设施。

## 4. 建议生命周期

```text
数据获取 → 数据校验 → 因子计算 → 策略信号 → 组合/仓位 → 风控否决
→ 生成建议 → 用户自行执行 → 记录人工结果 → 归因评估
```

每条建议必须至少包含：股票标识、动作、生成时间、参考价格或触发条件、建议仓位、止损/失效条件、有效期、因子依据、风险限制。

## 5. 运行模式

### 回测模式
使用历史数据，按时间顺序模拟信号和组合变化，纳入费用、滑点、涨跌停、停牌、T+1 等约束。

### 模拟盘模式
使用实时数据生成建议，记录假设成交和虚拟持仓，不产生真实交易。

### 建议模式
使用实时数据生成建议并通知用户；系统不假设用户一定执行，建议和实际成交分开记录。

## 6. 系统模块

1. **Data**：数据源适配、下载、原始数据和标准化数据。
2. **Quality**：完整性、时间对齐、异常值、数据新鲜度和可用性检查。
3. **Factors**：价格、成交量、估值、财务、行业、事件和市场状态因子。
4. **Strategies**：因子组合与信号生成，策略之间隔离。
5. **Portfolio**：目标仓位、组合约束、行业暴露和资金分配。
6. **Risk**：止损、回撤、流动性、异常行情和数据异常否决。
7. **Backtest**：事件顺序、成本、滑点和市场约束模拟。
8. **Simulation/Advisory**：模拟盘、实时建议、有效期和状态管理。
9. **Records/Reporting**：建议、人工成交、结果、绩效和归因。
10. **Operations**：日志、健康检查、数据延迟和失败告警。

## 7. 数据与回测原则

- 所有数据必须带时间戳和来源。
- 只能使用决策时已经可获得的数据。
- 财务数据按实际披露时间对齐，而不是简单按报告期日期对齐。
- 尽量保留退市股票和历史成分，避免幸存者偏差。
- 复权规则必须明确并可配置。
- 回测必须模拟手续费、印花税、滑点、成交限制、停牌和 T+1。
- 样本内、样本外和滚动测试分离。
- 记录策略版本、因子版本、参数、数据版本和运行时间。

## 8. 第一版技术建议

- Python：核心研究和运行语言。
- DuckDB + Parquet：本地历史数据和研究存储。
- Polars：数据处理。
- Pydantic：配置和数据模型校验。
- Typer：CLI。
- pytest：测试。
- Plotly：报告图表。
- SQLite：建议、模拟持仓和运行记录。
- 部署：本地 venv 直跑（start-all.sh 一键启停），不使用 Docker。

第一版采用模块化单体，不拆微服务。外部数据源必须通过适配器接入，策略不能直接调用供应商 API。

## 9. 第一版验收标准

- 在一台新电脑上按 README 完成初始化。
- 使用样例数据完成数据校验。
- 一个策略可以计算因子、生成信号并通过风险检查。
- 回测结果包含收益、最大回撤、交易次数、胜率、盈亏比、成本和基准。
- 同一份数据、配置和代码可以复现同一结果。
- 实时建议模式只输出建议，不存在下单模块。
- 测试覆盖核心数据模型、因子、信号、风控和回测边界。

## 10. 已确定的首期产品决策

1. 首期市场：A 股。
2. 首期标的：只做 60 开头、00 开头的普通股票；排除 ETF、创业板、科创板、ST/*ST。
3. 首期方向：短线、只做多、只生成操作建议，不自动交易。
4. 首期频率：按策略使用分钟线，竞价策略需要 9:20/9:25 快照。
5. 首期策略：竞价主力抢筹、连板捉妖、龙回头。
6. 建议输出：Telegram 用户 `7646550994`，架构上允许扩展多个渠道。
7. 实际成交：需要用户手动录入，系统用于建议与实际执行归因，允许 AI 辅助整理。
8. 历史回测：原计划从 2024-10-20 开始；因历史 9:20 竞价过程可能无法完整获取，当前暂缓完整竞价回测，优先保证交易日当天数据可脚本化取得。
9. 因子范围：包含价格、成交量、财务、市场情绪和新闻/事件因子。
10. 总体择时框架：所有策略必须经过市场情绪周期、主线/龙头状态和黑天鹅/监管风险检查。
11. 龙头暂定定义：当前市场连板数最多的股票；并列处理规则后续确定。

## 11. 待确认和待勘察的产品决策

以下事项保留到规则设计阶段，不阻塞数据适配器开发：

1. 各策略的具体建议仓位、止损、止盈和建议有效期。
2. “放量上攻”“连续放量”“封单相当大/封单小”的正式阈值。
3. “反复拉升/出货”的程序化识别公式。
4. 情绪周期的状态指标、阈值和状态转移规则。
5. 新闻 `impact` 等字段的业务刻度、黑天鹅判定和事件影响规则。
6. 题材主线强度的综合评分；题材连续 3 个交易日上榜已作为持续性基础规则。
7. 并列最高连板时的龙头处理规则；当前龙头定义为最高连板数股票。
8. 回测最低样本量、手续费、滑点和涨跌停成交规则。
9. 各数据源的授权、频率和并发上限的长期运行边界。

以下已经不再作为待确认项：

- 交易日当天 9:20/9:25 竞价数据：eltdx 已验证可取；历史回测暂缓。
- 三个首期策略和股票池范围：已确定。
- 建议输出 Telegram 与多渠道扩展：已确定。
- 用户手动成交录入和 AI 辅助归因：已确定。

## 12. 阶段路线

- **Phase 0**：确认本规格书。
- **Phase 1**：项目骨架、配置、数据模型、样例数据和 CLI。
- **Phase 2**：因子接口、一个基准策略和单元测试。
- **Phase 3**：回测引擎、成本模型和绩效报告。
- **Phase 4**：模拟盘和建议记录。
- **Phase 5**：实时数据、通知、监控和人工成交归因。
- **Phase 6**：多策略、组合优化和更复杂的模型。
